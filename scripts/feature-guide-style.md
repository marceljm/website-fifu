# Shared FIFU feature guide style

Use the shared feature-guide components and CSS as the visual pattern for every `/features/:slug/` guide. Inspect existing guides only to understand shared layout conventions; do not treat any individual card as the template for content or behavior. Reuse its site typography, spacing, colors, section headings, restrained blue accents, rounded borders, responsive behavior, and `feature-detail-cta` treatment. Keep feature pages in the site’s regular `Page` layout; do not use the Docs guide layout or add a competing visual system.

## Page structure

Follow this reading order, omitting only blocks that do not apply. These are page regions, not a fixed number of documentation sections. There is no required, maximum, or target section count; let the feature's verified workflow and complexity determine the structure:

1. **Page heading:** `Page` with eyebrow `FIFU FEATURE GUIDE`, the exact feature-card title, and a concise one-sentence lead. Treat about 25 words as a loose guide, not a target that requires padding. Avoid repeating the card description. Let the lead use the available page-header width; remove inherited narrow intro limits that leave unnecessary empty space and a short trailing line.
2. **Feature highlight:** use the dark navy `feature-highlight` section with a single-column reading order: concise introductory text, then a large illustration row. Add a short all-caps feature kicker, a plain-language heading, and one concise explanation. Include at most two short proof points only when they add information; omit claims already covered in the lead or explanation. Let the heading and explanation use the available inner width rather than retaining the old side-column text measure. Wrap naturally as the viewport requires. Keep copy and vertical padding compact; allow the large image to determine the remaining height rather than shrinking it to shorten the hero. Do not impose a fixed height or clip content.
3. **Feature illustration:** place exactly one newly generated static PNG, JPEG, or WebP image inside a full-width `feature-highlight-visual` row below the highlight text. Use `scripts/example.webp` as the visual reference: a clear illustrated workflow with simplified interfaces, consistent objects, minimal essential text, and a visible result. Match its horizontal, left-to-right composition and clarity, not its specific workflow or exact panel count. All illustrated steps must sit side by side in one row within the image, never vertically stacked. Use the available inner width on desktop and mobile; remove side columns, thumbnail max-widths, and excessive nested frame padding. Give the image concise alt text. Do not use browser screenshots or draw the illustration with HTML, CSS, SVG, canvas, or code.
4. **Guide sections:** reuse the shared section headings and icon tiles (`activation-feature-section`, `activation-feature-section-heading`, and `activation-feature-icon`), choosing the body structure that best explains each topic. Before the setup instructions, explain the problem the feature solves, its practical advantages, and when you need it. This explanation may live in the highlight if complete there; otherwise add a short purpose/use-case section without repeating the highlight. Use numbered steps (`activation-feature-steps`) for sequences, semantic tables for comparisons, definition lists for settings, and concise callouts for important conditions. Explain where to find the feature, how to use it end to end, relevant options, what happens, and source-confirmed prerequisites, limitations, or troubleshooting. Group related options so the page stays easy to scan. Add sections and subsections whenever they improve comprehension; never squeeze unrelated topics into a paragraph to match another guide's section count.
5. **Next step:** use the same restrained `feature-detail-cta`, linking back to `/features/` only.

Keep section margins, heading sizes, icon placement, colors, border radii, and mobile behavior consistent with the shared feature-guide layout. Reuse existing classes and shared CSS; avoid one-off classes and new page-specific styling. Small inline icon variations are fine when they explain the feature.

## Styling implementation and source review

- Separate consecutive paragraphs with a shared vertical gap of about `1em`, including paragraphs inside guide steps, notes, and grouped content. Use semantic `<p>` elements and shared CSS sibling spacing; do not simulate paragraphs with `<br>`, empty paragraphs, or page-specific inline margins. Preserve the shared content indent and responsive alignment. Ordinary wrapped lines within one paragraph keep normal line height; the extra gap marks a new paragraph only.
- Inspect the actual shared CSS and markup before applying classes. Check for selector collisions, inherited padding or borders, overridden display rules, and duplicate styles. Use scoped class names; avoid generic names such as `plan` on icons.
- Keep a clear reading hierarchy: page title, section headings, body, and supporting notes. Use comfortable line height, a readable text width, consistent space between sections, and clearly separated numbered steps.
- Give the page title enough space below the site header, including sticky-header offsets where applicable. Implement responsive spacing and anchor offsets in CSS; rendered verification is left to the user.
- When presenting multiple results or troubleshooting states, distinguish their meaning with explicit labels and appropriate icons, supported by restrained semantic colors. Do not give success, an available action, and an error the same generic warning treatment. Never rely on color alone; use shared status styles with readable contrast.
- Center icons in consistent tiles that cannot stretch or shrink. Align them with headings and avoid oversized backgrounds, stray borders, and inconsistent gaps.
- Ensure images preserve their aspect ratio and fit their containers. Inspect responsive rules for narrow screens, long labels, tables, and grids; prevent horizontal overflow.
- Let guide-section paragraphs use the same available content width as adjacent steps, tables, callouts, and code blocks, respecting the shared heading/icon indent. Do not inherit the old `.activation-feature-section > p` 810px cap or add arbitrary paragraph-only `max-width`/`ch` limits that leave a large unused area on the right. Apply this throughout the guide body, not only to the page lead and highlight. Use normal responsive wrapping; do not force single lines, shrink fonts, or remove meaningful paragraph boundaries. Keep intentional line breaks and whitespace in command/code examples.
- Repair the cause of styling problems. Do not stack arbitrary overrides or copy defects from existing pages. Keep shared changes minimal and inspect other uses of affected selectors.
- Implement the text-above-image layout in shared feature-guide styles and components, checking existing highlight consumers before changing selectors. Remove conflicting grid columns, visual max-widths, and fixed heights at every breakpoint; avoid a route-specific workaround. Preserve other guides' content and assets.
- Remove unnecessary breaks throughout the page introduction, including the page title, lead above the navy highlight, and highlight heading and explanation: inspect heading and paragraph markup plus inherited `max-width`, `width`, `ch` limits, grid tracks, and text-balancing rules. Do not add `<br>`, block spans, or literal preserved newlines to force a desktop line composition. Let the short introductory copy span its available inner width and wrap naturally. Avoid a stranded final word or short trailing phrase, such as a two-word line, when unused space is available. Inspect the shared `Page` header and lead selectors as well as feature-highlight selectors; fixing only the navy region is insufficient. If a short tail remains at common desktop widths, tighten the lead without losing necessary meaning or adjust the shared intro measure. Keep long-form blog and Docs article text at its established reading measure; do not apply those article constraints to the shared feature-guide section paragraphs. Do not use `white-space: nowrap`, shrink typography, or cause overflow to force a single line; wrapping on smaller screens remains necessary.

## Fresh rebuild on every run

- Rebuild the complete guide body and generate a new illustration whenever a feature card runs, including reruns. Research, outline, and draft independently from current plugin source; do not patch or paraphrase the previous guide or reuse its outline, evidence checklist, or artwork.
- Preserve the existing route, exact feature-card title, shared components and design, and unrelated content. Inspect old markup only to locate replacement boundaries and integration points. Replace this feature’s body and image after the new work is ready; do not delete shared files or other guides.

## Purpose, advantages, and when to use the feature

- Every guide must answer these questions before its first setup step: What problem or limitation does this feature address? What changes when you use it? What practical benefit does that give you? In which situations do you need it? Explain when it is unnecessary or optional if the source establishes that distinction.
- Research the existing behavior or data path, the feature's changed behavior, and the conditions that make it applicable. Connect the verified mechanism to a concrete reader benefit rather than merely listing controls. A task description such as "move data in batches" does not explain why the data needs moving or why batches help.
- Cover meaningful, distinct advantages using verified feature behavior and sound general technical knowledge, with relevant conditions and tradeoffs. Benefits need not be explicitly stated in the plugin source or bundled help. Use a short paragraph, use-case list, benefit cards, or a before/after table as appropriate; there is no required benefit count or mandatory extra section. Keep the explanation specific and avoid repeating it in the lead, highlight, and body.
- For maintenance or migration features, investigate what older state is being handled, what the current implementation needs, who is affected, and what operational problem the mechanism addresses. Use technical knowledge to explain the advantages of the verified architecture even when bundled help does not name them. For example, when the implementation moves relevant metadata out of WordPress postmeta and reads it from dedicated tables, explain that this can reduce growth and query pressure on the shared postmeta table and improve performance for affected operations. Tie this reasoning to the actual data paths; do not imply that all WordPress postmeta usage stops, that total storage necessarily shrinks, or that every site becomes faster.
- Keep settings, paths, supported values, implementation behavior, and prerequisites source-verified. For purpose and advantages, you may supplement that evidence with your best technical knowledge and reasonable causal inference. Explain the mechanism and its reader benefit clearly; use wording such as "can improve" or "helps reduce" for expected outcomes dependent on site conditions. Do not invent historical developer intent, benchmarks, measured gains, guarantees, or unsupported capabilities. In the private evidence/report distinguish verified mechanisms from inferred advantages and briefly record the reasoning. Missing explicit benefit text in source is not an evidence gap or a reason to mark the guide incomplete when a sound explanation can be derived.

## Writing and scanning

- For each guide, independently investigate the feature from scratch in the source archive, including relevant menus, settings labels, descriptions, help and translated strings, and the code behind them. Follow related identifiers and conditional controls to build as complete an inventory as the evidence supports; do not rely on existing guide copy or a previous iteration's findings.
- Address the site owner directly in second person, using clear actions and short sentences.
- Explain the complete source-confirmed workflow without repetition or unnecessary background.
- Use concise headings that name a task or answer a reader question.
- Explain the primary action and any essential prerequisite in the lead. When a feature involves separate stages or modes, clarify their relationship early rather than leaving readers to infer it from later sections.
- Prefer short, concrete section headings such as an action to perform or a status to understand. Preserve exact interface labels in the steps where readers need to find them; headings need not repeat a full settings path or use vague instructions such as "decide what to do next."
- Use numbered steps for workflows, grouped rows or short lists for settings, and callouts only for useful cautions or tips.
- Number only actions that must happen in order. Present independent controls, status meanings, command options, and troubleshooting cases as labeled rows, definition lists, or tables. Do not turn every section into the same numbered-step template.
- Give each workflow step one primary action and its immediate expected result. Separate prerequisite access requirements from navigation, and separate routine monitoring, pause/resume controls, recovery, and post-completion actions when they answer different questions. State timing conditions beside the affected control.
- Replace long semicolon-separated inventories with meaningful groups in a list or table. Keep supported content types, settings, and metadata categories complete without forcing readers to parse a dense paragraph. Use plain-language descriptions alongside necessary technical names.
- Make reading pleasant by organizing facts around the reader's task. Additional UI elements are explicitly allowed whenever they make the information easier to understand: comparison tables, definition lists, grouped cards, option grids, status panels, checklists, callouts, code-example panels, and contextual navigation. Choose the structure that fits the information rather than repeating numbered rows everywhere. Reuse existing components and styles, or extend the shared feature-guide patterns when needed; there is no fixed quota of UI elements.
- Interactive elements are allowed when they serve a clear reading task. Use semantic controls, accessible labels, keyboard support, visible focus, and appropriate state announcements. Keep prerequisites, main steps, and essential limitations visible; use disclosure controls only for supplementary material. Ensure static illustrations remain exactly one generated image rather than replacing them with coded UI artwork.
- Separate the main workflow from supporting conditions. Put coverage, compatibility, limits, and exceptions in clearly labeled notes, compact tables, or definition lists beside the relevant step or immediately after the workflow. Give recovery actions their own clear grouping. Avoid dense paragraphs that combine unrelated rules and navigation. Preserve all necessary facts without repeating them, and keep essential information visible rather than placing it behind an expandable control.
- Use semantic table headers and accessible note labels. Verify that tables, grouped content, and callouts remain readable on narrow screens, using contained horizontal scrolling only when needed. Do not hide essential information behind interaction. Choose structure for clarity, not to meet a quota of sections, cards, tables, or words.
- Avoid third-person product narration such as “FIFU says,” “the plugin provides,” or “users can.” State the behavior directly.
- Present information directly, without attributing it to documentation, tabs, source code, or research. Mention a tab or page when the reader needs it as a navigation step or location.
- For every card and every feature, make the guide self-contained. Never direct readers to plugin settings, Documentation/Help tabs, tooltips, or another source to learn information that belongs on the page. Research and verify that material, then explain the relevant coverage, supported values/services, requirements, limitations, exceptions, and troubleshooting directly. “The Documentation tab explains domain coverage,” “see Help for details,” and equivalent deferrals are forbidden for any topic. Settings paths must lead to a concrete action, such as changing an option, rather than substitute for an explanation. Supplementary links must leave the explanation understandable on this page. Report unverifiable necessary facts as evidence gaps in the completion report; do not invent them or redirect readers to find them.
- Reread all reader-facing headings, steps, notes, and troubleshooting for this direct voice. Keep source evidence in the private checklist and completion report.
- Avoid generic marketing copy, decorative labels, and empty sections.

## Technical examples and related features

- Make exact custom field names, meta keys, WP-CLI commands, shortcodes, code, and literal input values such as example URLs easy to recognize. Use semantic inline code for short literals and labeled code blocks for longer commands or JSON, HTML, and other multiline examples. Keep ordinary interface labels in prose, and do not put whole paragraphs in code formatting.
- Include a concise example when it helps someone complete the workflow. Verify field names, syntax, arguments, markup, and expected values against the plugin source; use clearly illustrative URLs and placeholders rather than real credentials or invented behavior. Explain what to replace and where to enter or run the example. Render code as text, not executable HTML, and preserve whitespace in multiline examples.
- Label each command example with its purpose and describe the source-confirmed scope and expected result. Distinguish a single batch from a complete workflow. Keep placeholder instructions consistent with the actual snippet: explain placeholders only when they appear, and identify concrete example values as values to replace.
- Put restart, reset, deletion, and other state-changing maintenance commands in their own labeled example, with the consequences and when to use them explained immediately before it. Do not combine them with routine commands in a block that looks like a script to run from top to bottom. Present flags, defaults, units, and scope in compact option rows when useful rather than a dense numbered paragraph.
- Reuse the site's existing code and link styles where suitable. Keep examples readable and accessible on narrow screens, with wrapping or contained horizontal scrolling for long lines. Avoid introducing a competing visual system.
- When a guide mentions a genuinely related feature, link its descriptive name to its existing, verified internal feature-guide route when available. Choose links that help the reader continue the task, avoid repetitive or forced links, and never invent routes or link to an unrelated page solely for SEO. Keep the next-step CTA linking to `/features/`.
- Place verified action links beside the step or result where readers need them, using descriptive, visibly recognizable link text. Relevant setup, recovery, renewal, or support links should be easy to find before the closing browse-features CTA. Verify destinations against existing site routes and source-confirmed URLs; never invent them. Keep the closing CTA visually restrained so it does not overshadow task-specific actions.

## Static feature images

Generate once, save, and embed. The user reviews visual quality later; no post-generation image inspection or quality-driven retries are required or allowed in the batch workflow. Basic file and embedding checks remain.

- Inspect `scripts/example.webp` with an image viewer before preparing each image-generation prompt, and supply it as a style reference to the image-generation tool. Create fresh feature-specific artwork; do not embed the reference as the finished guide image or copy its controls into unrelated workflows. This reference is permitted even though previous guide artwork must not be reused. Follow its visual workflow and horizontal composition, but reduce its text: the reference is not a requirement to reproduce headings or every interface label.

- Generate exactly one new feature-specific static image per run from the workflow independently verified in the plugin source. Save it as `<feature-slug>-guide-1.png` (or the corresponding JPEG/WebP extension) and embed it once inside the single `feature-highlight-visual` container. Do not reuse previous guide artwork or create separate step images, GIFs, animation frames, or sprite sheets.
- Generate artwork once with the image-generation tool; do not substitute screenshots or CSS/HTML/SVG drawings. Preserve proportions during saving and display. Scale both axes uniformly; pad only when necessary. Keep the palette, objects, and camera consistent across panels in the generation prompt. Save the first generated result without inspecting it or requesting quality retries.
- For every feature card, show a concrete representation of plugin usage: the source-verified input or control, the user action or automatic operation, and the visible result. Use a cropped, simplified interface or affected content, keeping only the context needed to understand the workflow. Do not invent controls or behavior.
- Show the real workflow rather than abstract symbolic substitutes. Simple directional arrows and numbered step badges are allowed as connectors, as in the reference; do not use puzzle pieces, gears, clouds, license-key symbols, or checkmark badges in place of actual controls and results. Avoid decorative logos and branding; retain an interface name only when needed to identify the source-verified control.
- Keep text to the minimum necessary to understand the action or result. Replace secondary interface copy, page titles, navigation items, descriptions, table contents, and other nonessential text with subtle light-gray horizontal strokes or rounded placeholder bars of varied lengths. These strokes represent omitted text within the illustrated interface; they must not replace the actual controls, affected media, or visible result. Use readable text only when a specific control, essential input value, or outcome cannot be understood visually. Preserve exact source-verified labels when retained. Omit step headings by default; numbered badges and the visible action are usually enough. Include a very short step heading only if essential. Do not include explanatory sentences, command examples, repeated feature titles, decorative labels, or tiny fake lettering. Put detailed explanations in the page text.
- Use a wide landscape composition with all workflow panels side by side in a single horizontal row, ordered left to right. Use light panel backgrounds, restrained right-pointing blue connectors, consistent objects, and large recognizable controls. Never stack steps top to bottom, wrap panels onto a second row, or use downward arrows to connect stages. This rule concerns the composition inside the generated bitmap; the page still places the entire image below the hero text. Choose the fewest panels that explain the action and result; do not force four steps for every feature. Avoid dense dashboards, tiny labels, and paragraphs embedded in artwork.
- Use the shared full-width `feature-highlight-visual` row below the text, with minimal framing and responsive proportional sizing (`width: 100%`, `height: auto` or equivalent). Remove thumbnail constraints rather than enlarging the asset inside a narrow container. Reuse shared styles instead of adding one-off styling.
- Image quality is reviewed manually by the user later. Do not open or inspect the generated result, run visual/OCR/composition checks, compare candidates, or regenerate for text, layout, readability, branding, or other visual defects. Inspecting the supplied reference before generation remains allowed.
- Plan legibility in the prompt: use large relevant controls, gray strokes for secondary text, only essential readable labels, and the fewest panels needed, all in one horizontal row. Do not switch to a taller, vertically stacked composition or create more files. These are generation instructions, not post-generation approval gates.
- Request sufficient resolution for the full-width layout and readable labels. Keep the complete explanation in accessible page text. Preserve horizontal step order and do not crop the bitmap into separate panels or rearrange its steps with CSS.
- Request normal, undistorted typography in the generation prompt. Do not perform post-generation typography inspection; the user will assess the result manually.
- Provide concise alt text describing the intended source-verified action or outcome, without claiming to have inspected the result. Verify the asset path and embed it with proportional responsive CSS.

## Completion gates and known regressions

- Manual visual review is pending by design for every guide. Do not block completion for unreviewed image quality, horizontal composition, rendered line endings, or responsive appearance. In the completion summary explicitly state that image and rendered-page visual review are left to the user.

- Apply shared usability guidance while writing and reviewing the source/CSS: clear actions and prerequisites, concise highlights, task headings, grouped supporting rules, contextual links, and responsive layout. This is an implementation review, not rendered visual approval; no browser, screenshot, or generated-image inspection is required.
- Review information organization as well as factual completeness. Split dense paragraphs containing unrelated rules into appropriate sections, tables, lists, or notes. There is no fixed section count for any guide; do not mark documentation complete while its structure makes necessary information difficult to scan.
- Before setting `documentation=true`, confirm that the reader can explain why the feature exists, which problem it solves, its advantages grounded in verified behavior and sound technical reasoning, and when to use it, without relying on the illustration or another guide. A guide containing only settings and procedural steps is incomplete. Include source locations for the underlying mechanisms and reasoning for inferred advantages in the completion evidence. Do not require the source to explicitly state every advantage; only missing essential behavior or a rationale that cannot be reasonably established requires `documentation=false` and `status=incomplete`.
- Verify that illustrations occupy a large row below the text rather than a side thumbnail, that independent actions are not presented as mandatory sequences, and that reset examples cannot be mistaken for routine setup. Check placeholder consistency and distinguish task-level statuses from overall statuses where both exist.
- Review the introduction markup and CSS for forced line breaks, obsolete width limits, and overflow risks. Apply the intended wrapping rules across breakpoint declarations. Rendered line endings and final responsive appearance are left to the user and must not prevent completion.
- Review body paragraphs and their ancestors for width constraints too. Text, code blocks, and callouts within the same guide section should share the available content width rather than alternating between a narrow paragraph measure and full-width blocks. Existing example guides are not authority for copying these constraints. This remains a source/CSS review; rendered wrapping is left to the user.
- Inspect shared-shell source for unrelated demo branding and placeholder footer text. Report such defects with their location; do not rewrite unrelated site content during a single-guide task. Rendered spacing review is left to the user.
- The `image` check means generation, saving, and embedding succeeded, not visual approval. Set it false for missing generation or failed delivery, never merely because visual inspection was skipped. The `styling` check means shared markup/CSS were reviewed and the requested layout implemented; it does not certify rendered appearance.
- Review all reader-facing copy for deferred explanations before marking documentation complete. Replace each informational redirect with the verified facts on the page, and confirm that settings navigation performs a concrete action. Any remaining informational deferral or unresolved necessary explanation requires `documentation=false` and `status=incomplete`. Apply this gate to every feature card on every run.
- Existing guides demonstrate layout conventions, not proof that their markup is correct. Replace any coded highlight in the assigned guide. Verify the final production HTML contains exactly the one reported image in `feature-highlight-visual`; merely saving an asset does not satisfy this requirement.
- Check technical styling in the regular `Page` layout. Existing `.guide-article code` rules only apply to Docs. Add or reuse shared, feature-scoped inline-code and pre/code rules with visible background, border, contrasting text, monospace font, and contained overflow. Any technical literals or commands used by the assigned feature must visibly use this styling. Inspect the matching selectors and cascade; do not mark this complete merely because `<code>` exists.
- Build a related-feature inventory from the entire guide, including navigation labels. Include related features mentioned in navigation paths as well as in prose. Check every related destination against the route implementation and production output. Report a decision and reason for each mentioned related feature; when a dedicated guide exists, link it at the useful point in the workflow.
- The runner rebuilds the site and checks production markup before advancing. Report formatting and links separately. File decoding, image count, asset paths, alt text, and embedding checks establish delivery only. They do not certify image quality or responsive appearance, which remain pending manual review.
